# Frontend architecture rules

- Adaptive maritime practice uses `/maritime-interview` with memory-only candidate state and end-only feedback; never replace existing company assessments or persist client scores. Why: server-owned sessions and manager reports belong to Phase 4.
- Interview voice uses optional browser speech recognition and synthesis with explicit microphone activation, editable text and unavailable-language fallback. Why: Phase 3 stays lean without telephony or new speech-provider charges.- Phase 4: AI interviews are server-owned sessions in `maritime_interview_sessions`; managers see a report only via `manager_maritime_report` when crew opted in and applied to their vacancy. Why: client cannot forge transcripts; consent-gated.
- Homepage training tracks come only from RPC `public_training_tracks` (titles/tags of published `training_modules`, no quizzes). Why: new courses appear on the public page automatically without leaking answer keys.
- Vacancy posting is open to any manager with a `manager_profiles` row (RLS `managers_*_own_postings`); `normalize_job_posting` sets `verified` from admin_approved OR company_verified only. Approval gates only Crew Search and Crew Desk. Why: third-party agents must post; the badge, not a block, signals trust.
- Principal CV templates: owner-private `principal_cv_templates` + `principal-templates` storage; reviewed mappings populate original DOCX/XLSX locally, declaration-gated. Why: no repeated AI cost or cross-manager access.
- Crew menu = `NAV_ITEMS` sections rendered by `GroupedNav`. Why: one menu.
- Crew priority boost only via RPC `boost_my_profile` (1d=1cr, 7d=5cr, extends) into read-only `crew_boosts`; `manager-search` floats boosted crew within each page with 3-hour rotation. Why: crew cannot forge visibility.
- Promotion assessments: manager requests via RPC `manager_invite_promotion` (own roster only) into `promotion_invites`; crew finishes `/maritime-interview?promo=` and `crew_complete_promotion` links the session; managers read only via `manager_promotion_board`. Why: result goes only to the inviting company, no client-forged links.
- Admin Crew Manning Matrix (`src/components/admin/CrewManningMatrix.tsx`) derives nationality/status via `src/lib/crewManning.ts` (declared → WhatsApp code → email domain) at read time; no stored guesses. Why: never overwrite what crew declared.
- Manager Crew Search (`/manager-search`): free browse + Quick CV; contact/full CV only after `reveal_contact` (1 credit, once per manager per crew via `contact_reveals`); `manager-search` returns `is_unlocked` + real contacts only for revealed crew and action `unlocked` lists the manager's roster. Why: never charge twice, no contact leaks.
- Crew Search (main crew database) is owner-only until the owner expressly opens it: hidden from manager menu/dashboard, `OwnerPreviewGate` + owner check in `manager-search`; managers search only their own applicants, Company Crew and roster; `/marketplace` browsing is public and linked from the homepage, while posting and `marketplace_contact` keep their server checks. Why: launch visibility without opening unfinished server paths.
- Maritime Brain is one component (`MaritimeMasterBrain`) used in Training and the main-menu Brain screen; photos go to `diagnose-equipment`, documents are read to text in the browser (`src/lib/brainAttachments.ts`) and sent to `bridge-chat`, never stored. Why: one AI hub, no duplicate screens, no file retention.
- Maritime Marketplace hubs (spares/yards/tech) live in `marketplace_items`; supplier contacts in seller-only `marketplace_item_contacts`; every inquiry/WhatsApp/email contact goes through RPC `marketplace_contact` (owner-preview check, charges `market_contact_credits` once per buyer+item when monetization is on). Filters/RFQ text in `src/lib/marketplaceExchange.ts`. Why: no contact leaks, never charge twice.
- Marketplace third-party sellers live in `marketplace_vendors` (vendor sign-up metadata `vendor_signup` skips crew profile creation; status changed only by admin). Until admin_settings `marketplace_open`='true', `/marketplace` is gated by `MarketplaceGate` and RLS shows each seller only its own items/ship listings; sellers work in `/marketplace/vendor`. Why: suppliers onboard privately without being mixed with crew or managers.
- Marketplace listing fees (vessel/spare/service) and supplier welcome credits live in `monetization_settings` and are charged by trigger `charge_market_listing` at insert (independent of the monetization switch; 0 = free); technical spec schemas/photo slots live in `src/lib/marketplaceSpecs.ts` stored in `specifications` jsonb; free-credit requests via `request_market_credits` → admin `admin_decide_credit_request`. Why: client cannot skip fees, and categories evolve without schema changes.
- Crew dispatches ("Voice of the Sea") live in `crew_dispatches`; trigger `crew_dispatch_guard` snapshots author rank/vessel from `crew_profiles`, forces status/counters and caps 5/day; photos in private `crew-dispatches/{uid}/` bucket (WebP compressed in browser). Why: crew cannot forge identity or engagement.
- Admin vacancy batches go only via RPC `admin_bulk_import_vacancies` (owner UID check, dedup_key skip, max 300) into `external_vacancies`. Why: agent can publish for the owner without opening insert rights.
- Apply routes are Email or WhatsApp only (plus internal SeaMinds/flyer view); a company website is never an application route and never records 'Applied'. Why: owner rule — applications must reach a real recruiter inbox.
- Email footers link to branded `/unsubscribe?f=<function>` (page POSTs to the function); List-Unsubscribe headers keep the direct function URL for one-click. Public links (Telegram, blog) use seaminds.life only. Why: never show the backend host to users.
- Route metadata uses Helmet; static overridable tags use `data-rh="true"`, with route-owned canonicals. Why: prevent duplicate tags and incorrect page identity.
- Vacancy Studio regressions guard: broadcast/export queries order `created_at` DESC; the manager dashboard always shows a count of live agency broadcasts (never silently hidden); the post-publish receipt stays until "Start new batch"; job cards hide placeholder values via `realText`. Why: 411 published adverts once looked "missing".
- Company Crew intake: approved managers create office records via RPC `company_crew_import` into `company_crew_records` (shared ID sequence `next_crew_unique_id`, docs in private `company-crew-docs/{uid}/{record}/`); crew accept at `/claim/:token` via `accept_crew_claim` (new accounts take the reserved ID, existing crew keep theirs, company entries appended with `source:'company'`, fleet link set active). Why: managers onboard rosters fast while each seafarer still gives explicit consent.
- Interview Studio results use paged RPC `campaign_candidates_v2` (search/filter/sort, max 100 per page) and click-through `manager_candidate_dossier` (campaign owner only; CV/contacts only for admin-approved managers; wellness flags excluded). Custom training briefings come from `training-module-draft` (manager-only, nothing stored, sent inside the invite text). Why: thousands of candidates without scrolling, consent-safe.
- Manager training radar: crew share progress by opening an invite link with `mt=<manager_profiles.id>` (RPC `crew_share_training` → `manager_training_links`); managers read only via `manager_training_radar`/`manager_training_detail` (20s polling, interview scores only when crew shared). Why: consent-gated live tracking without exposing private tables.
- Training invites: sending (any channel) calls RPC `manager_link_training_crew` (approved managers) — links existing crew by email/phone to `manager_training_links`, else stores email in `manager_training_invites`; trigger links on crew sign-up. Why: radar fills without waiting for the crew to open the link.
- Training email invites: sent via `send-training-invite` (manager-only, Resend, 150/day per manager, 10-min duplicate skip); never `window.open(mailto:)`. Why: mailto popups left a blank tab and depended on a desktop mail app.
